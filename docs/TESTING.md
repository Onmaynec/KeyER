# KeyER — проверка v0.1.1 на Windows

**Автоматические проверки:** CI компилирует приложение и выполняет тестовый ввод в буфер (100 детерминированных последовательностей с 30% ошибок, остановка, пауза, фокус, Unicode и комбинации клавиш). Реальный SendInput не запускается в тестах.

**Ручные сценарии на Windows 10/11:**

1. **Старт/стоп:** в обычном Блокноте поставить курсор, запустить горячей клавишей, проверить паузу, продолжение и стоп.
2. **Отсчёт:** начать кнопкой в KeyER, переключиться в Блокнот за 3 секунды. Проверить, что при отсутствии переключения ввод не идёт в KeyER.
3. **Фокус:** во время ввода переключиться на другой процесс: набор должен прекратиться.
4. **Unicode:** русский и английский текст, цифры, символы, кавычки, эмодзи, табуляции, пустые строки.
5. **Ошибки:** с вероятностью опечаток 20% и высоким шансом поздних исправлений убедиться в корректности результата на строках из букв. Уточнение: в редакторе с автозаменой/подсказками возможны отличия.
6. **Code:** проверить C#, Python, C++ и JavaScript в Visual Studio, VS Code и обычном Блокноте. Сравнить введённый текст с оригиналом, особенно скобки и отступы. Проверить ClearAutoIndent включённой и выключенной.
7. **Настройки:** изменить скорость, паузы и горячие клавиши, перезапустить программу, убедиться в сохранении. Создать и удалить пользовательский профиль.
8. **Конфликт сочетаний:** назначить занятую в Windows комбинацию; программа должна сообщить, что регистрацию выполнить нельзя, и вернуть предыдущие настройки.
9. **Проверка прав:** подтвердить, что обычный KeyER может не вводить текст в процесс, запущенный с повышенными правами.
10. **Установщик и portable:** запустить portable ZIP без .NET SDK; установить и удалить Inno-Setup-сборку. Проверить русские пути профиля Windows.

**Проверка производительности:** 30–50 тыс. символов с максимальной скоростью, паузой и отменой. Не обещать точность и совместимость до реальной проверки в целевых приложениях.

Автоматическая сборка CI выполняется на Windows runner. Это не замена реальному GUI- и end-to-end-тестированию.

11. **Хоткеи:** отдельно проверить Ctrl+Alt+F5/F6/F7 без Win, при использовании других приложений и при удерживании Ctrl/Alt. Набор не должен начинаться до отпускания клавиш.
12. **Восстановление:** после двух сохранений испортить settings.json в тестовом профиле Windows; проверить загрузку резервной копии и отсутствие потери настроек.
13. **Журнал:** инициировать контролируемую ошибку и убедиться, что diagnostics.log не содержит текста, вставленного пользователем.

## Приёмка Text 2.0 на реальных приложениях

Сравнить итоговый текст с исходным (с учётом нормализации переносов) после **полного**, а не прерванного набора. Отдельно проверить 0%, 5% и 30% ошибок. На каждом целевом приложении:

- **Блокнот Windows 10/11:** короткие и длинные слова, кириллица, цифры, знаки препинания, emoji, несколько абзацев. Проверить поздние исправления и точный итог при Enter/Tab по умолчанию.
- **VS Code (обычный текстовый файл):** временно отключить форматирование и автозакрытие, сравнить длинный документ, проверить выбор Delete/Backspace/выделения.
- **Браузер textarea:** Enter создаёт абзац; для Tab попробовать режим пробелов, так как физический Tab обычно переводит фокус на другой элемент.
- **Telegram Desktop/Web:** выбрать профиль «Переписка» (Shift+Enter). Проверить, что переносы не отправляют сообщение; не использовать тестовые сообщения в чужих чатах.
- **Разное:** проверка эмодзи, комбинированных Unicode-символов, маркеров списков, пустых строк и смешанных алфавитов.
- **Надёжность:** остановить/приостановить с активной ошибкой, переключить окно во время возврата курсора; убедиться, что нажатия не уходят в другое окно.
- **Настройки:** обновить настройки v0.1.x до 0.2.0, проверить сохранение пользовательских профилей и появление шаблонов Text; убедиться, что 0% ошибок действительно отключает все намеренные опечатки.

**Критерий:** добиться посимвольного совпадения в явно поддерживаемых редакторах без автоисправления; отступления в Telegram/браузерах документировать как особенности совместимости. Успешные виртуальные тесты CI сами по себе не подтверждают этот критерий.

## Приёмка Code Intelligence v0.3.0

**Автоматические проверки (виртуальный редактор):** сравнение исходника и результата после токенизации, распознавание строк/комментариев, точность набора после намеренных ошибок и повторного выделения имён, задержки перед функциями, ручной выбор языка.

**Ручные проверки на Windows:**

1. Откройте в KeyER файл .py, .cs, .cpp, .js, .ts, .go, .rs, .html, .json или .sql. Убедитесь, что Code отображает предполагаемый язык. Переключите язык вручную — он должен иметь приоритет перед расширением.
2. В обычном **Блокноте** в пустом документе наберите образцы каждого языка. Сравните результат с исходником (нормализуйте CRLF/CR до LF). Проверяйте 0%, 5% и 30% ошибок.
3. В **Visual Studio** и **VS Code** отдельно проверьте работу с автоотступами и автозакрытием скобок. Для контрольной проверки сначала отключите автоматические вставки IDE. Затем включайте их по одной и фиксируйте расхождения: v0.3.0 не читает настройки редакторов.
4. Выставьте CodeReviewPercent = 25 и повторите тест идентификаторов, включая длинные имена. Выделение последних букв не должно менять результат.
5. Проверьте Python triple quotes, C-style block comments, //, #, --, HTML comments, строки с фигурными скобками и кавычками.
6. Проверьте смену активного окна, паузу и остановку во время позднего исправления или повторного редактирования имени.
7. Проверьте сохранение настроек Code, выбор языка после перезапуска, а также сохранение профилей Text v0.2.0.

**Ограничение:** CI проверяет нажатия в виртуальном редакторе. Факт совпадения итогового текста в реальной IDE подтверждается только ручной проверкой целевого приложения и его конкретных настроек.

## Проверяемый ввод v0.4.0 — ручная приёмка IDE

**Перед тестированием:** Windows 10/11, KeyER 0.4.0, VS Code с установленным расширением KeyER VSIX и Visual Studio 2022 с доступным DTE. Создавайте только новые временные пустые файлы, чтобы не затронуть проектные данные.

1. **VS Code:** убедиться, что статус расширения показывает подключение. Включить «Проверить и исправить» в профиле Code. В пустом документе запустить код C#, Python, JS, JSON, включая сложные скобки и Unicode. После набора сравнить содержимое с оригиналом.
2. **Автоскобки:** при включённом autoClosingBrackets проверить, что окончательное содержимое исправляется в соответствии с исходником. В режиме «Проверить без исправления» расхождение должно только сообщаться и не перезаписывать документ.
3. **Отказ от небезопасного ввода:** с включённой проверкой попытаться начать в непустом документе, при двух курсорах и выделении. KeyER должен отказаться от запуска.
4. **Отключение связи:** выключить расширение/закрыть VS Code во время набора. KeyER должен остановиться, не продолжая вводить текст в другое окно.
5. **Смена вкладки:** переключить активный документ в том же VS Code окне во время набора; расширение должно отправить invalidated, ввод должен остановиться.
6. **Visual Studio 2022:** в новом пустом текстовом документе запустить проверяемый набор. Отдельно протестировать доступ к DTE под обычными правами, совпадение результата и разрешённое исправление.
7. **Права:** проверить KeyER без повышения и редактор с повышением прав: проверяемое соединение/автоматизация должны отказывать в запуске без ложных подтверждений.
8. **Форматирование:** проверить auto-indent, автозакрытие кавычек и IntelliSense в VS Code, затем сохранить файл — удостовериться, что после сохранения дополнительные форматтеры не меняют проверенный результат без уведомления.
9. **Состояние:** проверить Ctrl+Alt+F6/F7, отключение на середине сессии, ошибки и повторный запуск, Undo после API-исправления, отсутствие автоматического сохранения файла.
10. **Регрессия:** убедиться, что режим Text и Code с отключённой проверкой по-прежнему печатают как v0.3.0.

**Критерии:** проверяемый набор не изменяет чужой или непустой документ; не продолжает ввод после смены окна/вкладки; сообщает точный итог. Для VS Code результат в пустом документе после разрешённого исправления должен совпадать с исходником посимвольно. Если проверка или исправление не удалось, пользователю отображается ошибка, а приложение не утверждает об успехе.

**Автоматическая проверка:** C# regression runner + Node тесты расширения в GitHub Actions. Они не заменяют интерактивного тестирования.
