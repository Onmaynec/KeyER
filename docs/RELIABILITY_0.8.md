# KeyER v0.8.0 — Reliability & Compatibility

## Назначение

Релиз повышает устойчивость ввода при переключении окон, неверном выборе целевого приложения, Windows UAC и случайных физически зажатых клавишах. Внешний вид KeyER Studio сохраняется; в нижней консоли добавлены кнопки **«Проверить окно»** и **«Отчёт»**.

## Совместимость с окнами Windows

Встроенный инспектор \`TargetCompatibility\` использует Win32 для проверки:
- найдено ли окно и существует ли оно на момент проверки;
- не принадлежит ли активное окно самому KeyER;
- совпадает ли выбранный HWND с текущим foreground;
- не свёрнуто и не зависло ли приложение;
- запущен ли целевой процесс с повышенными правами, когда KeyER работает без повышения.

Для определения повышенных прав используется \`OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)\`, \`OpenProcessToken(TOKEN_QUERY)\` и \`GetTokenInformation(TokenElevation)\`. Если система не разрешила прочитать уровень прав, он помечается неизвестным; KeyER не утверждает, что отсутствующие сведения доказали полную совместимость.

**Важно:** успешный результат — только предварительная проверка окна, не гарантия приёма SendInput или корректности текста. Некоторые терминалы, игры, браузеры и редакторы перехватывают или блокируют синтетические клавиши. KeyER не отключает UAC и не пытается обходить системные ограничения.

### Ручная диагностика

1. В главном окне нажмите **«Проверить окно»**.
2. В течение трёх секунд переключитесь в целевое приложение и поставьте курсор.
3. KeyER инспектирует окно и покажет диалог: результат, имя процесса и действия для исправления проблемы.
4. Можно самостоятельно скопировать короткий отчёт без секретов.

Проверка доступна только когда нет другого запущенного набора. Кнопка Stop отменяет отсчёт проверки.

### Автоматическая проверка перед стартом

Любой реальный запуск после Ctrl+Alt+F5 или кнопки Start проходит тот же preflight. Для окон, которые не отвечают, свёрнуты, неактивны или требуют большего уровня привилегий, ввод **не начинается**. При переключении окна между проверкой и вводом движок дополнительно проверяет целевой HWND.

## Защита ввода по мере работы

### Привязка к процессу

WindowsTypingDevice запоминает PID целевого окна на время одного сеанса. Перед каждым вводимым действием проверяет:
- окно всё ещё существует;
- оно не принадлежит KeyER;
- оно остаётся активным;
- связанный PID не изменился.

Это дополняет прежнюю проверку HWND, защищая от повторного использования идентификатора окна другим процессом. Не следует воспринимать этот механизм как защиту от всех сторонних вмешательств в систему.

### Защита от случайных модификаторов

При старте KeyER, как и раньше, ждёт отпускания Ctrl/Alt/Shift/Win после глобального хоткея. **После начала физического ввода** последующее нештатное удержание этих клавиш приводит к исходу \`Interrupted\` и остановке дальнейших нажатий.

Это особенно важно при исправлениях ошибок и перемещениях курсора: неожиданно зажатый Ctrl мог бы превратить обычную стрелку в переход по словам. Управляемые KeyER симулированные сочетания остаются атомарными.

## Отчёт последнего запуска

Кнопка **«Отчёт»** рядом с прогрессом доступна после завершения попытки. Сводка хранится **только в оперативной памяти**, исчезает после закрытия KeyER и никогда не содержит исходник, содержимое редактора, имя файла или заголовок чужого окна.

В отчёте указаны:
- исход \`Completed\`, \`Cancelled\`, \`FocusLost\`, \`Interrupted\` либо \`Failed\`;
- краткое имя процесса, без путей и названий документов;
- число **обработанных** символов, всего символов и длительность;
- рекомендации для следующего действия.

\`Processed\` — это индикатор движения движка по исходнику. Он **не равен количеству символов, гарантированно принятых целевым редактором**: во время исправлений, автоматического форматирования и сбоя SendInput фактическое содержимое может отличаться.

Отчёт можно скопировать в буфер обмена по явному нажатию. Никакой автоматической телеметрии или фоновой отправки нет.

## Отказ от опасного автовосстановления

KeyER 0.8.0 сознательно не предлагает кнопку «Продолжить с последнего символа»: пользователь мог сменить редактор, начатая опечатка может быть частично исправлена, а IntelliSense мог добавить символы. Для восстановления:
1. Прочитайте отчёт о причине остановки.
2. Проверьте реально набранный текст в целевом приложении.
3. Удалите повреждённый или лишний фрагмент вручную, если требуется.
4. Выберите корректное окно и начните новый сеанс из нужного исходника.

При необходимости точного итогового кода используйте интеграцию IDE 0.4–0.8, если редактор и условия проверяемой сессии поддерживаются.

## Проверки

В Windows CI:
- тестируется матрица результатов инспектора (нет окна, окно KeyER, потеря фокуса, зависание, свёрнутость, повышенный целевой процесс и \`Ready\`);
- проверяется остановка при включении физических модификаторов в Text и Code, без лишних нажатий;
- проверяется новый сеанс после прерывания без автоматического повторного воспроизведения старого текста;
- проверяются границы прогресса, отчёты и конфиденциальность;
- создаются настоящие WinForms-окна, включая новое окно совместимости, а также снимок интерфейса;
- сохраняются регрессии Text, Code, Human Behavior и VS Code extension.

Автоматические тесты не заменяют ручную проверку физического SendInput. Особенно важно испытать поведение с Windows 10/11, несколькими мониторами, UAC, Блокнотом, VS Code и Visual Studio 2022.
